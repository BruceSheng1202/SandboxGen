# Known limitations and preserved behavior

The initial release preserved the reference version's functionality. The 2026-09-12 Linux/Windows consistency update changes the active framework as described in [platform-consistency.md](platform-consistency.md). Historical experiment snapshots, reports and success statuses remain unchanged.

The subsequent [static tool robustness update](static-tool-robustness.md) adds working strings/grep pagination, explicit option validation, preserved truncation markers, runtime-aware tool descriptions and narrower parser fixes. Tool availability still depends on the deployed image; these fixes do not establish model accuracy.

1. **Tool protocol recovery can fail.** In reference batch R6, the Architect repeatedly produced invalid tool calls for `data_x86_64`. Normal correction and finalization did not recover the run. It ended with `protocol_stalled` before dynamic execution.
2. **Historical prompts contain inconsistent backend descriptions.** The active prompts now describe both Linux and Windows capabilities, reject incompatible guests and require compatible DLL exports. Backend facts are supplied before Scout runs, and Architect configuration is validated before execution. Historical model output still reflects the older contradictory instructions.
3. **Historical Linux syscall summaries conflate attempts and success.** New Linux evidence schema 2 retains syscall outcomes and errno, distinguishes opening from positive-byte writes, and marks unknown socket protocols. Old `file_written`/`executed`/connection lists alone do not establish successful behavior. Even successful writes or connections do not prove persistence or C2 activity.
4. **Collection coverage still differs across platforms.** Both platforms now gate execution on observed sample startup and collection health. A successful Linux exec or Windows process/DLL load does not prove that the intended payload completed. Lists still have length limits, and behavior originating from Windows services may be classified as background noise. Legacy Linux reports without the new startup evidence cannot certify execution validity.
5. **Complete retention of raw material is not guaranteed.** Current cleanup and archival paths do not guarantee preservation of every strace, PCAP, temporary output, or file inferred by a model. Report fields do not establish that the underlying sensor data is available for review.
6. **The backend does not implement every CAPE feature.** QEMU still has no CAPE `human`, sleep skipping, memory dumps, FakeNet, or model-driven guest provisioning. Both platforms expose effective configuration and unsupported options; recovery no longer adds unsupported CAPE options to QEMU. Scout's environment/resource/monitor proposals are not applied automatically. Linux observes the traced process group until exit or timeout; Windows enforces the full observation window. This difference is explicit in capabilities/acknowledgements rather than silently treated as identical.
7. **Isolation, architecture, and dependencies limit behavioral coverage.** Downloaders, environment-specific payloads, and DLLs may not be fully triggered. A Windows ImageLoad event proves loading only.
8. **Report delivery does not establish accuracy.** Known issues include evidence misinterpretation, unsupported inferences, and mapping errors. Not all reports have undergone detailed semantic scoring.
9. **Source code alone cannot reproduce the full environment.** Original images, datasets, provider state, and reference containers are not distributed with the repository. Dependency locks describe the release validation environment, not a package-for-package copy of the old VMs or containers.
10. **Direct Python execution and the production wrapper provide different isolation.** Direct execution may use the legacy fork-based static parsing path. Passing offline tests does not validate the isolation configuration of a real deployment.
11. **External dependencies and installation media require maintenance.** Base OS images, guest software, and Windows evaluation terms change over time. Source tests and Python vulnerability scans do not cover VM/container operating systems or media that are not included.
12. **Sample identity checks do not guarantee immutable content.** `SampleIdentity.matches()` and `RunContext.open_sample()` compare device and inode, without rechecking the recorded SHA256. They detect replacement with a different inode, but not in-place changes or reuse of a deleted inode. Keep input files and their containing directories protected from modification throughout a run. The path-swap regression test creates the replacement before removing the original so that inode allocation does not make the test nondeterministic; it does not validate protection against inode reuse. Strengthening this boundary requires a separate functional change and regression validation.

Record future functional fixes as new versions and validate them with consistent inputs and acceptance rules. A sample's successful report delivery on an older version does not establish correct analysis on a newer version.
